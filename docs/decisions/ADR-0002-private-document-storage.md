# ADR-0002: Private document storage for the self-hosted MVP

**Status:** Accepted T01 storage boundary; T02 upload profile below is a provisional MVP technical decision. Retention and off-host backup policy remain later work.
**Date:** 2026-10-27

## Context

The project runs a separate Next.js web app, Next.js API and PostgreSQL in Docker Compose. Only PostgreSQL currently has a named persistent volume. EPIC-04 must keep receipt, bill and vehicle originals private, available after a container rebuild, and recoverable with their metadata. The browser reaches the API through the web's same-origin rewrite; only the API may read stored bytes. EPIC-05 needs the same original document for receipt extraction and later review.

## Decision

### Storage boundary

For the **single-host, self-hosted MVP**, add a private Docker named volume `document_data` mounted **only** into the API container at `/var/lib/household-finance/documents`. `DOCUMENT_STORAGE_ROOT` names this absolute root; production must fail closed if it is absent, outside the mounted volume, unavailable or unwritable. Local `pnpm dev` uses the Git-ignored `data/documents` directory as an explicit development root. Do not mount the volume into the web or recurring-worker containers, copy bytes into the image, put them under either app's `public/` directory, or use the container's ephemeral writable layer. The API storage module accepts bytes/streams and generates each key with 256 random bits encoded as 64 lowercase hex characters. The disk path is a **flat** child of the configured root derived only from that validated key; original filenames remain safely normalized display metadata. Validate the key again when reading it from metadata, reject symlinks for the root and file, and use exclusive create/no-follow file operations. No request field may supply a path or storage key. The key is an internal locator, **not** a bearer credential or authorization token.

Use an API-owned storage capability with narrow operations `stage`, `finalize`, `open`, `exists` and `reconcile`; `stage` returns only an internal handle, never a path for an HTTP response. Restrict directories/files to the API process (for example 0700/0600) and run that process without root privileges once volume ownership and Prisma startup are validated. T01 adds no HTTP upload/download route, public URL or delete capability.

### Metadata and crash consistency

Add one household-owned `Document` metadata row with opaque `id`, `householdId`, `uploadedByUserId` (a scalar retained if a user later leaves or an account is removed), unique `storageKey`, lifecycle status (`STAGING`, `AVAILABLE`, `FAILED`), safe display filename, declared and detected MIME types, byte count, full-file SHA-256, `createdAt` and `availableAt`. Metadata creation receives household/uploader identity only from the authenticated API context after fresh membership validation, never from browser-selected IDs. The household foreign key uses `RESTRICT`; add `(householdId, id)` uniqueness for future same-household receipt/bill/vehicle foreign keys. Household ID, uploader ID and storage key are immutable, including across status changes. The final byte count/hash/type may be nullable during `STAGING`, but an `AVAILABLE` row must have all final metadata; enforce this in the API and with a SQL check. Index `(householdId, status, createdAt)` and `(householdId, sha256)`; never make hashes globally discoverable or globally unique. Following the approved EPIC-04-T04 policy, content uniqueness may be enforced only within a household. Future references use `Document.id`, never a storage key. Do not add deletion before original retention is decided.

Database and filesystem writes are not one atomic transaction. The internal T01 capability creates only a non-readable `STAGING` row, writes a unique temporary file **on the same volume** while counting and hashing complete bytes, flushes/syncs the file, then finalizes to the generated key without replacing an existing file and syncs the directory before changing the row to `AVAILABLE`. On Linux, an exclusive same-directory hard link followed by temporary-name removal provides no-replace finalization; a plain overwriting rename does not. T02 later adds format/size validation before finalization. Only the final database update makes the row available. A failed or interrupted write removes its temporary file and marks the row `FAILED` where possible. A crash after finalization but before the database update leaves non-readable `STAGING` metadata and orphan bytes; a crash after the update retains the synced final bytes and `AVAILABLE` row. Startup runs a read-only reconciliation and exposes anomalies for an operator command: stale staging rows, orphan temporary/final files, and available rows with missing or mismatched bytes. Reconciliation does not silently delete originals or promote a row; reads fail closed on missing/corrupt bytes. Never return an available document ID before bytes and metadata agree.

### Access boundary

For T03, prefer API-controlled streaming from a household-scoped route such as `GET /api/v1/households/{householdId}/documents/{documentId}/content`. Recheck the current session and `read` membership on every request, then query by **both** `documentId` and `householdId` and require `AVAILABLE` before opening the key from server-side metadata. Missing and foreign IDs have the same 404 response; no session gets 401. Do not disclose the key, host path, full-file hash, or another household's metadata. Use `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`, a safe detected content type and, for the first release, `Content-Disposition: attachment` for untrusted originals. This trades inline previews for a smaller same-origin content-execution risk; a later preview flow can use a separately isolated origin or a reviewed safe viewer. No permanent or presigned URL is needed with the local volume.

T02's multipart upload must check current `financial-write` membership (`OWNER`/`MEMBER` under the existing policy), an exact allowed web origin/CSRF rule suited to multipart requests, request size and rate limits, detected file signature, and declared MIME. The current JSON-only CSRF helper cannot be reused unchanged for multipart; preserve its origin check while adding a purpose-built media-type rule. Do not buffer an unbounded request with `Request.formData()` before enforcing a byte cap. The pinned Next.js 16 Route Handler uses the Web Request/Response APIs; validate the chosen streaming parser and runtime against the installed `apps/api/node_modules/next/dist/docs/01-app/01-getting-started/15-route-handlers.md` and [official Route Handler reference](https://nextjs.org/docs/app/api-reference/file-conventions/route) during implementation.

### T02 provisional upload contract (2026-10-27)

This is an implementation baseline, **not** a user-approved final format/limit policy. `POST /api/v1/households/{householdId}/documents` accepts exactly one `file` part, a stable UUID `Idempotency-Key`, and no other fields. Use the Node.js Route Handler runtime and pin `busboy` 1.6.0 (plus its matching TypeScript declarations) as the one streaming multipart parser; the package is not currently a direct API dependency. Bridge `Request.body` to the Node parser with backpressure, never call `formData()` or buffer the whole file. The parser must reject absent/invalid boundary, any extra file/field/part, truncated file, malformed stream and abort. Set `files: 1`, `fields: 0`, `parts: 1`, small header/name limits, and a file limit above the exact 20 MiB threshold so an exactly 20 MiB file is not rejected merely for reaching the parser's limit. Independently count decoded file bytes and raw request bytes: reject an empty file, more than 20 MiB (20 × 1024 × 1024) of file data, or more than 20 MiB plus 64 KiB of multipart envelope. `Content-Length` may reject early but never substitutes for streaming counts. Check fresh membership and exact allowed `Origin`/multipart content type before consuming the body; a separate multipart validator reuses the JSON CSRF helper's origin policy.

Detect type from a bounded leading prefix and bounded structural trailer while streaming: JPEG SOI/EOI, PNG signature/IHDR/IEND, PDF `%PDF-` and trailing `%%EOF`, and ISO-BMFF `ftyp` with bounded box length and recognized HEIC/HEIF major or compatible brands. Allow only `image/jpeg`, `image/png`, `image/heic`, `image/heif`, `application/pdf`; require exact declared MIME agreement with the detected family. Reject unknown or ambiguous brands, truncated structures and mismatches with `4xx`, without conversion. This checks container signatures and obvious truncation; it is not a full image/PDF decoder or malware scan. Keep only the small prefix/trailer in memory, then pass the file stream to T01's private staging capability and finalize only after parser completion and validation.

Add nullable `Document.uploadRequestKey` (UUID) with unique `(householdId, uploadedByUserId, uploadRequestKey)` in a new additive migration. Claim it in the initial `STAGING` insert, so concurrent attempts with the same key cannot stage a second document. On an existing `AVAILABLE` row, consume and validate the retry, then compare complete SHA-256, byte count, detected/declared MIME and normalized display name; exact match returns the same minimal document ID/metadata, difference returns `409`. Existing `STAGING` returns retryable `409` while in progress; `FAILED` or stale `STAGING` never replays success and requires a fresh key after reconciliation. No key/hash/storage path appears in responses. The key is scoped to household and uploader; a different key with identical bytes is the separate T04 duplicate decision.

The existing PostgreSQL also supports the provisional **10 attempts per authenticated user per UTC clock minute** across API processes. Add one `DocumentUploadRateBucket` row keyed by `(userId, minuteStart)`; before reading any file bytes, atomically insert or increment only while `count < 10` using `INSERT ... ON CONFLICT DO UPDATE ... WHERE ... RETURNING`. No returned row means `429` with bounded retry guidance. Count authorized attempts, including malformed bodies and retries; prune expired buckets separately. This fixed-minute window can permit a boundary burst and is an explicit MVP trade-off, not a rolling 60-second guarantee. No Redis or in-process-only counter is needed.

Implement T02 in three ordered, manually checked slices: **(1) persistence and request guard** — developer owns `apps/api/prisma/schema.prisma`, one new migration, a small PostgreSQL rate/idempotency helper under `apps/api/src/lib/`, and reusable origin validation in `apps/api/src/lib/csrf-protection.ts`; **(2) bounded parser and signatures** — developer owns `apps/api/package.json`/`pnpm-lock.yaml` for pinned busboy/types and `apps/api/src/lib/document-upload.ts`; **(3) route integration** — developer owns `apps/api/src/app/api/v1/households/[householdId]/documents/route.ts` and only the narrow T01 storage change needed to claim the key in `STAGING`. Each slice uses synthetic local files and the task's manual checks; no web code or automated suite is part of this MVP.

### Paired backup and restore

T05 should back up PostgreSQL metadata and `document_data` as **one labeled recovery set**, with a manifest of document count, byte sizes and SHA-256 values. A simple, reliable self-hosted procedure is a short write-maintenance window: stop new uploads/metadata writes, drain in-flight uploads, take `pg_dump` and a volume archive, then resume writes. Store the recovery set outside both containers, with restricted access and encryption appropriate to the deployment. Restore into a disposable environment first and compare every `AVAILABLE` metadata record with the expected private file hash; missing or corrupt linked bytes fail the restore check. A database-only backup is incomplete. The final off-host destination, retention and encryption policy belong to the deployment owner and are not assumed here.

Docker named volumes persist independently of containers and are the Compose-native choice for this setup; see [Docker's volume documentation](https://docs.docker.com/engine/storage/volumes/). Docker Desktop also notes that volume contents require separate backup from container images; see [Docker's backup guidance](https://docs.docker.com/desktop/settings-and-maintenance/backup-and-restore/).

## Alternatives

| Option | Fit and trade-off |
|---|---|
| Private object storage (S3-compatible/MinIO) | Useful for multiple API hosts, independent storage operations and future short-lived signed access; adds a service, credentials, network failure modes, object lifecycle and a separate backup/security configuration before the MVP needs them. A private bucket alone does not establish household authorization. |
| Docker named volume (selected MVP) | Fits the existing single-host Compose stack and keeps the API in control of every byte read; requires explicit backup/restore and cannot be shared safely across multiple API hosts without a later migration. |
| Bind mount | Easy to inspect on one host, but depends on host path/permissions and is easier to misconfigure as a public or unbacked directory. |
| PostgreSQL large objects or bytea | Makes database/byte consistency simpler but enlarges the database and its backup, complicates streaming and later object-storage migration. The epic explicitly separates file bytes from metadata. |
| Public static directory or permanent signed URL | Rejected: either bypasses fresh household authorization or creates long-lived access to private originals. |

## Consequences and implementation order

T01 first adds the metadata model, private API-only volume and storage module; T02 adds validated upload and multipart CSRF/size handling; T03 adds authorized streaming; T04 adds a household-only duplicate outcome; T05 adds backup/reconciliation runbooks and a synthetic restore exercise. Because T01 itself has no upload endpoint, its acceptance checks should use only synthetic internal files and metadata. Do not treat a database row alone as a working document.

This is an **accepted T01 design**, not an implemented fact; do not update `docs/architecture.md` to describe it as present until code, Compose and migration exist. The architect reviewed the architect/developer/reviewer/tester agent responsibilities and the `api-and-interface-design` and Prisma setup skill mappings; no role or installed-skill change is needed for this scoped decision. Recheck the mappings when the storage boundary is implemented.

## Open policy decisions

- Deployment owner: choose the off-host backup destination, retention and encryption/access policy; the single-host local volume is settled for T01.
- Product owner: confirm after real-device evidence whether the provisional JPEG/PNG/HEIC/HEIF/PDF, 20 MiB and fixed-minute 10-attempt limits fit household use; `VIEWER` remains read-only in T02.
- **Resolved 2026-10-28 (EPIC-04-T04):** exact-byte duplicates in the same household do not create a second document and safely identify the existing document for opening. Another household may independently store the same bytes; no cross-household existence signal is allowed.
- Product owner: retention of originals linked to posted receipts, bills and vehicles, and whether/when a delete flow can exist.
