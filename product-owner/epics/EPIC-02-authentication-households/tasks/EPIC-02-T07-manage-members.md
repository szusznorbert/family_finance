# EPIC-02-T07: Manage household members

## Goal and user value

Household members can see who has access; removals and departures must always preserve at least one OWNER.

## Scope

Provide a member list, OWNER-controlled member removal and member self-departure in the API and web. Roles are chosen when inviting; T07 has no general role-change action or role selector. A sole OWNER may select an existing member and atomically promote that member to OWNER while leaving the household in the same transaction. Enforce the T03 policy for actor and target roles. Removal or departure takes effect for subsequent API requests.

## Product decision update — 2026-10-26

The user removed general role editing from T07. A member's role is chosen at invitation; there is no MEMBER↔VIEWER edit, standalone promotion, generic role PATCH, or role selector. A sole OWNER may select an existing MEMBER or VIEWER only as part of leaving: the target becomes OWNER and the departing OWNER's membership is removed in the same transaction. This decision supersedes earlier role-change and two-step transfer assumptions. The implementation record below is historical until the implementation update replaces it; manual verification is coordinated with the T06 fixture owner.

## Acceptance criteria

- [ ] OWNER, MEMBER and VIEWER see only their selected household's member names and roles. Full account e-mail addresses are visible only to OWNER and each member for their own account; pending invitation address labels remain OWNER-only.
- [ ] Only OWNER can remove another member, including another OWNER if at least one OWNER remains. MEMBER and VIEWER cannot remove others. There is no general role-change action, role selector, role `PATCH` route, or standalone owner-transfer route.
- [ ] Every role can leave their own household. An OWNER can leave directly only while another OWNER remains. A sole OWNER must select an existing MEMBER or VIEWER; that member becomes OWNER while the departing OWNER is removed in one atomic transaction. Failure changes neither membership. Audit records for promotion and departure/removal are written in the same transaction without PII or secrets.
- [ ] Concurrent removals and departures cannot leave a household without an OWNER. Removed users lose access on their next API request; a promoted OWNER has OWNER permissions on their next request. Household and target identifiers are tenant-scoped, with 401/403/404 behavior as specified above.

## Implementation update — 2026-10-26 (narrowed scope)

- Added `GET /api/v1/households/[householdId]/members` for all current members. The response always includes names, roles and `isSelf`; only OWNER receives member user IDs and every member's e-mail, while MEMBER/VIEWER receive only their own e-mail.
- The target route `DELETE /api/v1/households/[householdId]/members/[userId]` is OWNER-only and removes another member. There is no `PATCH` role-change route. `DELETE /api/v1/households/[householdId]/members/me` permits self-leave; for a sole OWNER, its optional `transferToUserId` promotes an existing MEMBER/VIEWER and removes the departing OWNER atomically. The standalone `/members/transfer` route has been removed.
- Removal and leave/transfer re-check actor membership and the OWNER invariant inside PostgreSQL serializable transactions. Serialization conflicts return `409`. Audit events record target promotion, member removal and departure in the same transaction; no e-mail, IP, token, user-agent or payload is recorded.
- `apps/web/src/app/members-manager.tsx` is connected beside `InvitationsManager` in `apps/web/src/app/households-panel.tsx`. It provides the member list, OWNER removal buttons and the sole-OWNER leave-with-transfer selection. It has no role selector or role-save control. The two managers have distinct, household+role keyed component identities.
- Every mutation uses the shared `WEB_ORIGIN` + JSON CSRF guard and returns `Cache-Control: no-store`; target IDs are scoped to the authorized household. Self-leave uses the `read` policy so VIEWER can leave.
- **Checks run:** Prisma format and schema validation passed; the audit migration was applied and Prisma Client generated by root. API/web `typecheck`, targeted ESLint for T07 API and web files, and `git diff --check` pass. No automated test suite or production build was run.
- **Manual verification status:** The read-only pass is recorded above. Mutation cases remain pending approval and coordinated synthetic fixtures. The prior MEMBER→VIEWER request was not retried; its failed attempt left the fixture role at MEMBER and general role editing is now outside scope.
