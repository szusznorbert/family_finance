# EPIC-04-T02: Accept validated document uploads

## Goal and value

A permitted household member can submit a photo or PDF and receive a private document ID only when the original file is safe to accept and durably stored.

## Scope

- Add a household-scoped upload path using T01's storage/metadata capability. Validate byte size, declared type and detected file signature on the server; reject an unsupported, mismatched, empty or oversized file before it becomes usable.
- Derive household access and uploader identity from the current session and membership; apply write-role and CSRF protections to the multipart mutation. Never trust request-supplied household ownership, MIME label or filename as proof of type.
- Return a document ID and minimal safe metadata for later receipt/bill/vehicle linkage. Handle failed or interrupted uploads without a successful-looking document or ledger record.

## Implementation checklist

- [x] Upload request-key/rate-limit schema, migration, and API-side request/CSRF guards.
- [x] Bounded streaming multipart parser and image/PDF signature, MIME, field, and size validation.
- [x] Authorized upload POST route with idempotent claim/replay handling and private-storage integration.
- [x] Response limited to safe metadata; static checks and the documented HTTP smoke completed.
- [x] Dedicated bounded, same-origin web upload forwarder avoids Next.js rewrite body truncation for the application upload flow.

## Acceptance criteria

- [ ] A permitted member can upload each accepted synthetic image/PDF format and receive a household-scoped document ID; unsupported type, mismatched signature, empty file and an oversized file fail with clear responses and leave no usable document.
- [x] A request without a session, with insufficient role, or targeting a foreign household cannot create a document in that household; the browser never receives a storage key or permanent public file URL.
- [ ] An interrupted or failed upload does not create a receipt, bill, vehicle record or ledger entry and does not leave a metadata record advertised as available when its bytes are missing.

## Dependencies

T01 storage and metadata; EPIC-02 fresh household authorization. EPIC-05-T01 consumes this upload capability. Coordinate accepted type/size policy before implementation.

## Verification checklist

- [ ] In the existing local app/API with synthetic files and accounts, upload each allowed format, wrong-extension/wrong-signature examples, empty and oversized files; inspect status, returned metadata and private storage. Repeat as no-session, `VIEWER`, `MEMBER` and foreign-household users under the accepted role policy. Do not create project copies or automated tests.

## Non-goals and open questions

No AI extraction, receipt draft, general document gallery or financial posting. Decide exact image/PDF formats (including HEIC/HEIF handling), maximum bytes, request-rate limit and upload role matrix. A filename is display metadata only and requires safe normalization if retained.

**Scope and files:** The first independently verifiable foundation slice introduces a nullable UUID `Document.uploadRequestKey`, a unique constraint over household/uploader/key, and a per-user UTC-minute rate bucket stored in PostgreSQL. It includes a new additive migration, `apps/api/prisma/schema.prisma`, small rate/idempotency helpers under `apps/api/src/lib/`, and a shared Origin check in `apps/api/src/lib/csrf-protection.ts`. Existing JSON-only endpoint behavior remains unchanged. `docs/architecture.md` describes only implemented state. The parser, POST route, T01 storage changes, and web UI are outside this slice.

**Dependencies and verification:** This builds on the T01 Document model and storage capability, and EPIC-02's fresh authorization checks. The actual idempotency claim is made later during route/storage integration. Prisma validate/generate, API typecheck, lint, and diff-check are required; apply the migration only to a safely identified local database. Manually test the helper with synthetic data only: 10 accepted attempts and the 11th rejected in one UTC minute, an independent quota for another user, replay for matching AVAILABLE metadata, conflict for mismatch, and no success for STAGING/FAILED. This does not satisfy the full T02 acceptance list.

**Open decisions:** 20 MiB, HEIC/HEIF, and 10 attempts per minute remain ADR-0002's provisional MVP technical profile, not final user-facing product decisions. The first slice implements the fixed value of 10; it does not define deletion/retention policy.

**First-slice manual verification log — 2026-10-28:** Under Node 24.22.1, `pnpm --filter api exec prisma validate`, `pnpm --filter api prisma:generate`, `pnpm --filter api typecheck`, and targeted ESLint checks on the three affected `src/lib/` files passed. `git diff --check` reported no errors. `prisma migrate status` stopped on the local `localhost:5432` database with `Schema engine error: undefined`, so the migration was not applied; runtime synthetic rate/idempotency checks and post-migration database-constraint checks remain open. Full T02 acceptance is still incomplete.

**Slice and dependencies:** This is a one-file, household-scoped multipart upload built on the private API-only storage in T01 under accepted [ADR-0002](../../../../docs/decisions/ADR-0002-private-document-storage.md). T01's named-volume restart and database-constraint runtime checks remain open; T02 can be planned, but durable operation is not considered complete until those checks close. T03 authorized reads, general duplicate detection in T04, EPIC-05 receipt extraction, and any web upload UI are outside this slice. Signed-in mobile QA for EPIC-03 remains a separate open item.

**File ownership:** The `developer` owns the new POST in `apps/api/src/app/api/v1/households/[householdId]/documents/route.ts`, a focused streaming multipart/MIME/limit helper in `apps/api/src/lib/document-upload.ts`, and the reusable multipart-capable portion of Origin validation in the existing `apps/api/src/lib/csrf-protection.ts`. They may touch T01's `apps/api/src/lib/private-document-storage.ts` only for a necessary, agreed narrow extension. If durable idempotency needs a new field/mapping, the same developer owns `apps/api/prisma/schema.prisma` and a new additive migration; the T01 migration must not be rewritten. Before writing Next.js route code, read `apps/api/AGENTS.md` and the installed Next.js Route Handler documentation. No web file or public file path is in scope.

**Request, authorization, and response:** `POST /api/v1/households/{householdId}/documents` accepts `multipart/form-data` with one `file` field and a stable UUID `Idempotency-Key` header. Based on fresh Better Auth membership, `OWNER`/`MEMBER` (`financial-write`) may upload and `VIEWER` may not; no session returns `401`, a foreign household uses the standard indistinguishable `404`, and an insufficient role returns `403`. The JSON-only CSRF helper cannot be called unchanged for multipart requests: validate the exact allowed `Origin`, multipart media type, and size before reading bytes. Return successful `201` only after `AVAILABLE`, with minimal `{ document: { id, displayName, detectedMimeType, byteSize } }` data and `no-store`; do not expose the storage key, internal path, full hash, original bytes, or permanent URL in responses or logs.

**Proposed MVP limits, not yet user-approved:** one file per request, up to 20 MiB; JPEG, PNG, original HEIC/HEIF, and PDF, with server-side signature/brand and declared-MIME matching. This is a working assumption for a photo-based receipt flow that includes iPhone use; no automatic conversion. Empty, corrupt, mismatched, or oversized data returns `4xx`; enforce the cap during streaming, not only from `Content-Length`. Target local rate limit: 10 upload attempts per user per minute, returning `429` when exceeded; the architect/developer records the technical approach for reliable counts across multiple API processes. If the selected parser cannot safely verify HEIC/HEIF brands or bounded multipart streaming, raise that as an open decision before coding instead of silently dropping the iPhone format.

**Idempotency and errors:** A repeated request with the same household/uploader/key and identical complete bytes returns the prior available document ID; the same key with different bytes returns `409`. Competing or interrupted attempts can produce at most one `AVAILABLE` document, and a retry cannot treat a `STAGING`/`FAILED` row as success. This is request retry behavior, not T04's duplicate policy for identical content submitted with different keys. Validation, storage, or database errors must not leave a usable document record; remove temporary files or make them visible as read-only reconciliation anomalies. Do not create a receipt, bill, vehicle, or ledger record.

**Synthetic manual acceptance:** On the running local API, use two test households. An `OWNER`/`MEMBER` successfully uploads a small JPEG/PNG/HEIC/PDF; the response ID identifies that household's `AVAILABLE` metadata and private bytes. Reject `VIEWER`, signed-out, and foreign-household callers; invalid signature/MIME, empty, corrupt, and over-20-MiB streams leave no available record. Replay with the same key and bytes returns the same ID; different bytes return `409`. After an interrupted stream, reconciliation reports any residue and there is no false success. Check rate limits, response/log secrecy, relevant typecheck/lint/diff-check; do not add an automated suite. Open product questions remain whether 20 MiB, 10 attempts per minute, and the HEIC/HEIF format set fit real iPhone photos; do not present them as approved user decisions.

### Second slice: bounded multipart parser — historical read-only plan, 2026-10-28

**Boundary, dependency, and file ownership:** This slice builds on the first persistence/request-guard slice contract, following the [three-slice T02 sequence in ADR-0002](../../../../docs/decisions/ADR-0002-private-document-storage.md). The `developer` owns only `apps/api/package.json`, `pnpm-lock.yaml` (pinned `busboy` 1.6.0 and compatible TypeScript declarations), and the new parser/signature helper `apps/api/src/lib/document-upload.ts`. This slice does not add or change an API route, storage, Prisma schema, migration, idempotency, or CSRF code; the third slice connects the parser to the authorized route and private staging. The parser converts the Node Route Handler `Request.body` stream into a bounded byte stream that preserves backpressure, without `formData()` or a full-file buffer.

**Manual acceptance:** With synthetic multipart streams, accept exactly one `file` part and no fields; reject a missing boundary, extra file/field/part, overly long header/name, abort, malformed stream, or truncated stream. With `files: 1`, `fields: 0`, and `parts: 1`, the parser separately counts the decoded file (maximum 20 MiB) and total request (maximum 20 MiB + 64 KiB); accept an exactly 20 MiB file, reject one byte more or an oversized envelope, and do not rely on `Content-Length` instead of the streaming cap. Identify JPEG, PNG, PDF, and HEIC/HEIF signatures/brands from a bounded prefix/trailer and ensure they match declared MIME; reject empty, unknown, truncated, and MIME-mismatched content. On slow consumption, abort, or oversize, backpressure reaches the producer, the stream closes, and no temporary resource remains; the parser does not create an available document. The developer records actual manual sample, typecheck/lint/diff-check results and does not write an automated test suite. The format/limit profile remains a provisional MVP basis, not a final user decision.

### Third slice: authorized POST integration — historical read-only plan, 2026-10-28

**File boundary and dependency:** This slice builds on the completed contract for the first slice's `document-upload-rate.ts`, `document-upload-request.ts`, and multipart CSRF guard, and the second slice's `document-upload.ts` parser. A `developer` owns the new POST in `apps/api/src/app/api/v1/households/[householdId]/documents/route.ts` and may make only a minimal, agreed extension to `apps/api/src/lib/private-document-storage.ts` for the initial `STAGING` claim of `uploadRequestKey` and later persistence of validated MIME. Do not rewrite the first two slices' helpers, schema/migration, web, or T03 download route. The route runs on the Node runtime under the installed Next.js Route Handler rules.

**Operation order and response:** The POST requires a fresh Better Auth session and household `financial-write` access (`OWNER`/`MEMBER`; `VIEWER` gets `403`, a foreign household `404`, and no session `401`). Enforce the exact same-origin multipart guard, UUID `Idempotency-Key`, and PostgreSQL per-minute rate bucket before reading the body. Then stream one file to private staging through the bounded parser; do not return `AVAILABLE` before full parser/signature validation, hash/byte matching, and durable finalization. The same key plus same validated content returns the same document ID; different content returns `409`, and in-progress or failed state cannot replay as success. Replays also undergo byte and MIME validation. On error/abort, there is no usable document; clean staging residue or expose it through reconciliation. Do not create a receipt/ledger row. Successful `201` or matching replay returns only minimal ID/name/detected MIME/byte count with `no-store`, without storage key/path/hash/bytes/permanent URL.

**Synthetic manual smoke and open status:** In two test households, upload small JPEG/PNG/HEIC/HEIF/PDF files; verify OWNER/MEMBER success and reject VIEWER/signed-out/foreign callers. Invalid MIME/signature, empty, truncated, aborted, and oversized streams must leave no `AVAILABLE` record. Check same/different idempotent retries, `429` on the 11th attempt in a minute, and response/log secrecy. Use synthetic local data only; no automated suite. The last recorded migration status for the first slice was **not applied** because of `Schema engine error: undefined`; recheck the current local DB status and safely apply the migration before runtime route smoke. T01 named-volume restart and database-constraint checks, and signed-in mobile QA for EPIC-03, remain separate open items; do not claim full T02 acceptance from static checks alone.

### Web upload forwarding follow-up: read-only plan — 2026-10-29

**Scope and likely files:** The installed Next.js 16.4.3 external rewrite buffers only 10 MiB by default and can truncate a larger multipart upload before the API's streaming 20 MiB limit sees it. Add one dedicated, same-origin, Node.js web Route Handler under `apps/web/src/app/api/document-uploads/[householdId]/route.ts` that forwards only POST uploads as a bounded stream to the existing API endpoint. Change only the upload URL in `apps/web/src/lib/document-upload-client.ts`. Keep the existing document-list GET rewrite untouched. Record the new web-to-API path in `docs/architecture.md`; review affected agent assumptions.

**Dependencies and acceptance:** The existing API remains authoritative for session, household membership, CSRF, MIME/signature, idempotency, and storage. The web handler must forward only required cookie/origin/content-type/idempotency headers, preserve safe API statuses and responses, and reject a request above the API's 20 MiB + 64 KiB multipart envelope with a controlled JSON `413` even without `Content-Length`. A valid near-limit upload must reach the API intact; small uploads and existing auth/CSRF outcomes must remain unchanged. No storage key, file bytes, or credentials may be logged or included in the response.

**Verification and open decision:** Run web typecheck, lint and `git diff --check`; the tester repeats synthetic direct-API versus browser-path HTTP checks, including an oversized request with no `Content-Length`, and inspects the existing test DB plus private temporary storage for residue.
