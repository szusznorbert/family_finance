# EPIC-04-T04: Detect household duplicate files

**MVP phase: `MVP now` — explicitly authorized by the user.**

## Goal and value

Help a household recognize an already uploaded original without creating duplicate document records or exposing another household's documents.

## Scope

- Compare the complete-file hash captured at upload with available documents in the same household. Exact-byte duplicate uploads do not create a second document; the response safely identifies the existing household document and offers an open action.
- Handle near-simultaneous identical uploads deterministically. Never use a global existence signal that confirms whether another household has uploaded the same bytes.
- Keep duplicate detection separate from receipt approval and ledger posting; a duplicate file must not silently create or suppress a financial entry.

## Implementation checklist

- [x] The upload path hashes the complete byte stream and creates a private spool before creating a `Document`.
- [x] A PostgreSQL transaction-scoped advisory lock serializes the authoritative same-household/hash lookup and insert without changing or removing legacy duplicate rows.
- [x] A matching hash returns a safe duplicate/replay response; both upload UIs link to the existing document.
- [x] A fresh client-side navigation resets transient document-library state; a list request that exceeds its deadline exposes a retryable error instead of leaving the loading indicator indefinitely.

## Acceptance criteria

- [x] Re-uploading identical synthetic bytes within one household creates no second document and returns a safe duplicate result that identifies the existing document for authorized opening. Different bytes do not match based on filename or declared MIME type.
- [ ] The same bytes uploaded in a second household create that household's own document; neither response, error, nor application log reveals the other household's document, owner, hash, or existence. **Partial:** household-local creation and 404 isolation were verified; a buffered server-log batch contained only access summaries, but individual cross-household lines were not conclusively correlated.
- [x] Concurrent identical uploads in one household deterministically leave one document and return the existing-document duplicate result to the competing upload. No response refers to unavailable content or silently loses the original.

### Concurrent write boundary — architect review, 2026-10-28

**Initial implementation rationale — superseded after read-only duplicate gate, 2026-10-28:** The first design proposed a household/hash partial unique index, but a read-only aggregate of the authorized existing test DB showed two legacy duplicate groups. The migration was not applied. To preserve these rows without a cleanup or corrective migration, the final writer uses a transaction-scoped advisory lock. Under that lock it loads only the authorized household's `AVAILABLE` same-hash candidates in deterministic order, verifies their stored bytes, then returns one verified duplicate or creates a new `AVAILABLE` row. If metadata matches exist but no file verifies, the upload fails closed with a generic error; it creates no second record and returns no unusable ID. Another household's hash/record is never queried. The private spool and exclusive hard link remain; an ambiguous non-unique DB error retains the final file for a possibly committed row, and read-only reconciliation reports an orphan if no row exists.

Idempotency is checked after hashing the complete file: compare an existing `(householdId, uploadedByUserId, uploadRequestKey)` row with the current fingerprint; an identical retry is replayed, while different content conflicts. Earlier request-key claiming at stream start and an `UPLOAD_IN_PROGRESS` response during upload may change; T04 acceptance specifies the final one-record outcome for concurrent requests with the same or different keys, not the early in-progress response. A failed, unfinalized request creates no `Document` or `FAILED` row; remove its temporary file, while a filesystem orphan left after a crash/ambiguous commit may be reported by read-only reconciliation. Prisma `STAGING`/`FAILED` statuses remain, but the current T04 writer does not write them.

**Updated continuation plan — 2026-10-28:** Change only `apps/api/src/lib/private-document-storage.ts`, the upload Route Handler, and the already un-applied partial-index migration (remove it). Use an explicit `ReadCommitted` Prisma transaction, acquire `pg_advisory_xact_lock` keyed from `householdId + sha256`, query all matching `AVAILABLE` rows ordered by `createdAt,id`, verify each stored file against expected size/hash, and either return the first verified candidate or create the new row while the lock remains held. If matching metadata exists but all candidate files fail verification, fail closed with a generic non-enumerating upload error; do not insert a second row or disclose an unusable ID. The repository currently has one `Document.create` call. Keep the existing non-unique Prisma index; no schema or database migration is needed. No product decision remains open. Run Node 24 typecheck/lint/diff-check; the tester may later run HTTP smoke against the existing test DB without changing the legacy duplicate fixtures.
