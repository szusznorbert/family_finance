# EPIC-04-T01: Establish private storage and document metadata

## Goal and value

Give the household a durable, private place for original files and metadata so later receipt, bill and vehicle flows can refer to the same document without creating public file links.

## Current status — 2026-10-30

**Completed and manually verified for T01 scope.** The named volume preserved synthetic bytes and their metadata across an API-container restart; database foreign-key and immutability checks passed in rolled-back transactions. Twenty-seven verified local originals were copied into the canonical Compose volume. The two test-data records whose originals were absent from both roots are now `FAILED`; an independent comparison confirmed that only their status changed and their historical metadata was preserved. All 30 remaining `AVAILABLE` records match private files by byte count and SHA-256, and reconciliation reports zero anomalies. An isolated synthetic metadata-write failure produced no available row, was detected as an orphan by reconciliation, and its own file was removed. The existing T03 manual check confirms a direct public URL returns 404.

## Scope

- Choose a self-hosted private storage boundary and document metadata contract that links each file to exactly one household and its uploader. Record generated opaque storage key, declared/detected type, byte size, complete-file hash and timestamps needed by later upload, access and duplicate checks.
- Keep file bytes outside web public assets and the database; persist them across service restarts. Coordinate the database record and stored bytes so failed writes do not leave a usable record pointing to missing content.
- Expose a narrow server-side storage capability for T02/T03. Do not expose raw storage paths/keys in client responses or accept a browser-provided path as the storage location.

## Implementation checklist

- [x] Document metadata model and additive Prisma migration implemented.
- [x] API-only private storage capability with a generated key and stage/finalize/open/exists/reconcile operations.
- [x] Persistent Compose volume assigned to the API container and a read-only reconciliation path.

## Acceptance criteria

- [x] A file stored through the internal capability receives a generated, non-guessable key and household-linked metadata; no permanent public URL or browser-visible storage path is created.
- [x] File bytes survive a normal app/container restart in the selected persistent store, and a failed metadata/file write is detectable and does not appear as a valid available document.
- [x] The metadata can be linked by future receipt, bill and vehicle records without changing a document's household ownership; the internal storage path cannot be chosen through a request field.

## Dependencies

EPIC-02 household and user identity. Establish the backend, persistence and retention assumptions before the T02 upload route. Coordinate any metadata relation used by EPIC-05-T01.

## Verification checklist

- [x] Inspect the selected storage configuration and metadata migration using synthetic files, then restart the relevant service and confirm bytes and metadata remain paired. Confirm the web public directory and direct static URLs cannot expose the file. Run only relevant static checks; no automated test suite.

## Non-goals and remaining questions

No user-facing upload or download in T01; those are T02/T03. **Resolved by accepted ADR-0002:** the self-hosted MVP uses the API-only persistent Compose volume, with a Git-ignored local development root. Do not add deletion before a retention policy is accepted. Reconciliation is read-only and reports broken/orphaned state; it does not silently repair or delete originals.

- **Bounded T01 scope and sequence:** First settle the private storage backend and lifecycle of bytes versus metadata. Then add a household/uploader-linked document metadata model and migration, API-only storage abstraction with generated opaque keys, and persistent API mount/configuration for both local development and Compose. Keep storage outside `apps/web/public`, the Docker image's ephemeral writable layer, and browser-accessible paths. - **Data and safety contract:** Metadata must include immutable household ID, uploader identity, generated storage key, original byte count, declared and detected media type, complete-file SHA-256 and creation time. Do not make the hash globally unique: T04 must be able to detect same bytes per household without signaling another household's existence. The storage key is an internal locator, never a bearer credential. A failed write must not yield an available document row; recovery must identify orphan bytes or broken links. Storage-path construction must not accept caller input or traverse outside the private root, including via symlinks.
- **Dependencies:** EPIC-02's current session and household identity; T02/T03 consume this contract. Coordinate field names and relation constraints with EPIC-05-T01's future receipt reference. The current authorization helper remains the API policy boundary; T01 does not grant a browser operation or change role rules.
- **Acceptance and manual verification:** With only synthetic local bytes, exercise internal storage/metadata creation and inspect the generated key, metadata relation, byte count/type/hash and private on-disk location. Restart the API/container and confirm the bytes and row remain paired. Force a synthetic file or metadata failure and verify no usable successful row is advertised; inspect and reconcile any orphan. Try a generated-key lookup through web public/static paths and confirm it is unavailable. Check that local bytes stay ignored by Git and excluded from the image build context. Run schema validation, relevant static checks and `git diff --check`; record exact observations without adding or running an automated test suite.
- **Open decisions before code (historical; storage choice later resolved):** At this planning date the architect/product owner still needed to choose the backend and define commit/reconciliation behavior. ADR-0002 subsequently accepted the API-only persistent volume, local development root and stage/finalize/reconcile contract. Account-removal behavior and overall deletion/retention remain separate policy questions; do not add a delete endpoint before retention is accepted.
